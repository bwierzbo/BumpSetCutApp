# Making the rally-classifier dataset trainable: footage-type confirmation, negative-label coverage audit, exporter plan, independent evaluation footage

The owner's decision of 2026-11-03 ("Owner Decision — BumpSetCut Temporal Rally Classifier") merged PR #136 (`6d6f97f`) as research and preparation work, kept the preregistration [EXP-20261103](experiments/EXP-20261103-temporal-rally-classifier-prereg.md) at `proposed`, and asked for the next workstream: "make the classifier dataset genuinely trainable without compromising the existing split, exposure, or holdout safeguards", with four priorities (A footage-properties confirmation, B negative-label coverage audit, C the exporter, D independent evaluation data). This document is that plan. It is written from the code on `main` at `6d6f97f`; file references are `path:line` on that commit. Nothing in it is authorised to run: no training, no export, no bulk processing, no annotation written or changed, no automatic confirmation of recording types, no RallyLab Phase 2 (D-031), no protected footage opened.

The companion protocol for priority B is [RALLY_CLASSIFIER_COVERAGE_AUDIT_PROTOCOL.md](RALLY_CLASSIFIER_COVERAGE_AUDIT_PROTOCOL.md); its seeded sample draw is `scripts/rally_classifier/coverage_audit_draw.py` (standard library, tests in `scripts/tests/`).

## 1. Priority A — footage-properties confirmation for the 34 candidate recordings

**Objective.** A person confirms, for each of the 34 declared-complete recordings (readiness §3), whether the footage is `continuous` or `edited`, and for an edited one which spans break time — written into the existing `FootageProperties` record so that `TrainingEligibility.assess` (unchanged) yields the negatives verdict. No competing source of truth: the record at `<project>/footage-properties/<safeName>.json` (`FootageProperties.swift:18, 164-165`) is the only place the type lives; the split manifest, the work queue and the exporter read it from there through `SourceRegistry`.

**Why a list-driven command rather than the Phase 2 UI.** Phase 2 (D-031) is the detection job, the scan import as proposals, and the properties UI, each on the owner's go-ahead; it is not started by this plan. For 34 recordings a reviewed headless command that writes **confirmed** records from an **owner-authored list** is the smaller change and follows two existing patterns: `--set-provenance` (one transaction per write, rollback on failure, `ProjectsModel.swift:1022-1061`) and `--confirm-youtube-source-ids` (preview by default; a report with prior values and proposed changes is written and read back **before** anything changes; `--apply` applies; ambiguous rows untouched; the reversal is printed; `HeadlessProjects.swift:775-812`). The owner chooses between this route and waiting for the UI (decision D5 in §6).

**The owner's input: a confirmation list.** One JSON file the owner writes by hand (or fills from a template the command prints), e.g. `manifests/footage-properties/confirmations-2026-11-xx.json`:

```json
{"schemaVersion": 1, "confirmedBy": "<owner>", "reviewedWith": "RallyLab Live-tag / Rally times view on the original (not the proxy) where timing matters",
 "recordings": [
   {"video": "bch_ele_ovc_land_self_02", "recordingType": "continuous", "note": "self-recorded iPhone, untrimmed"},
   {"video": "bch_ele_sun_port_self_03", "recordingType": "edited",
    "spans": [{"start": 84.1, "end": 103.3, "traits": ["slowMotion"], "note": "scan slowSeg; replay of the point before"},
              {"start": null, "end": null, "traits": ["zoom"], "note": "zoomed throughout; not time-breaking"}]},
   {"video": "grs_ele_dusk_port_self_03", "recordingType": "unknown", "note": "could not establish; leave not_assessed"}
 ]}
```

Rules the command enforces (all in the shared operation, not the CLI wrapper, per `CLAUDE.md`): refuse any name in the withheld closure (`ReservedVideos.lineageWithheldNames`); refuse a `video` that is not an admitted card; `recordingType: unknown` writes nothing (a person declining to confirm is not a record); a span's traits must be from `FootageProperties.Trait`; spans are written with `origin: confirmed`, `by: confirmedBy`, `at: now`, `source: "owner list <sha256 of the list file>"`; `recordingTypeBy/At` set; `sourceFingerprint` = the card's fingerprint at write time (so a later file swap quarantines, `SourceRegistry.swift:153-156`); an existing record with a **different** confirmed type is not overwritten without `--replace` and the report says so; proposed spans already in a record (none today; Phase 2's later) are kept, never promoted; the preview report `manifests/footage-properties/<stamp>-{preview|applied}.{json,md}` lists per recording the prior record (if any) and the proposed one, is written and re-read before any `Store.save`; `--apply` saves one record per recording via `FootageProperties.Store.save` (atomic, validated, `FootageProperties.swift:202-208`); a failed save stops the run and the report notes what was and was not applied; the command prints how to reverse (delete the listed record files, or re-run with the prior values the report carries). No ledger row: confirming a type is not a use of the footage for a model; the record itself carries who and when.

**What the owner looks at, per recording (≈ 3 minutes each, ≈ 2 hours for 34).** The decision rubric, written into the list's `note`:

| Observation | `recordingType` | Spans |
|---|---|---|
| Self-recorded on the owner's iPhone, one take, not trimmed or edited in Photos (the card's `originKind`/uploader say so; the scrub proxy shows no cuts) | `continuous` | none |
| Self-recorded but trimmed at the edges only | `continuous` | none (a clip that starts mid-rally is a cut-range matter when #135 lands, not an edited recording, `FootageProperties.swift:24-30`) |
| Online (YouTube) or any file where the scan flagged slow segments, hard cuts or zoom (`bch_ele_sun_port_self_03`: slow 84.1–103.3 s, 15 cuts; `grs_ele_shade_land_self_02`: zoom to 4.67×, no slow segments; `grs_ele_dusk_port_self_03`: 7 slow segments, borderline) — the owner watches the flagged places on the original | `edited` with each time-breaking span (`slowMotion`, `replay`, `montage`, `cameraAngleChange`) listed; a zoom alone is a trait that does not break time | as observed; the scan's numbers are hints, never copied blindly |
| Cannot be established (no original at hand, ambiguous) | `unknown` → nothing written | — |

Online recordings in the 34: `bch_onl_ovc_land_onl_02` (+`_v2`, `_v4`), `grs_onl_shade_land_onl_02`, `grs_onl_sun_land_onl_01`, `ind_onl_bright_land_onl_01_v2` (+`_v3`): the scan did not flag them, but they are the population where real edits live (scan README), so each gets the same look.

**Relation to cut ranges (D-030, #135).** A confirmed time-breaking span is "a reason to mark a cut range there, never a second mask" (`FootageProperties.swift:24-30`). Until #135 is on `main`, a confirmed span restricts the recording's negatives (`negativesRule`, `TrainingEligibility.swift:102-112`) and that is the correct, conservative state. After #135, the owner marks the cut in the live pass (X/⇧X) and the exporter masks it; the span record stays as the characterisation. The gate G2 is clarified accordingly (§6, and the amended row in the preregistration).

**Deliverable of A (a separate reviewed RallyLab PR, after the owner picks the route):** `--confirm-footage-type <list> [--apply] [--replace]` in `HeadlessProjects.swift` (dispatch pattern `:133-551`), the shared operation in `FootageProperties.swift` or a new `FootageConfirmation.swift`, `RallyLabTests`: preview writes nothing; apply writes a validated record with fingerprint, by, at, confirmed spans; withheld name refused; non-admitted card refused; `unknown` writes nothing; existing different type refused without `--replace`; a failing save leaves earlier records applied and the report says so; the usage header updated. Expected eligibility after a full pass: `continuous` ones → negatives `standard`; `edited` ones → `restricted` (positives only, non-rally time `UNKNOWN`); unconfirmed → unchanged. The readiness audit is re-run afterwards into a new dated file (readiness §8).

## 2. Priority B — negative-label coverage audit (summary; the protocol is the companion document)

The owner's requirement: confirming `continuous` is necessary but "does not independently prove that every rally was marked"; before training, "prepare a small, independently reviewed coverage-audit protocol for the legacy declared-complete recordings" that finds missed rallies and wrongly labelled dead time, with provenance that distinguishes legacy-declared from Stage 1 coverage, and never promotes unreviewed time.

[RALLY_CLASSIFIER_COVERAGE_AUDIT_PROTOCOL.md](RALLY_CLASSIFIER_COVERAGE_AUDIT_PROTOCOL.md) specifies: the unit of review (every **unmarked interval** of a recording, edges included, since that is where a missed rally hides); the verdict rubric per interval (`clean`, `missed_rally`, `play_bleeds`, `non_rally_activity`, `not_footage`, `unresolved`); a two-stage sample (stage 1: 12 recordings, 4 per surface, drawn with a fixed seed from the 34 by `coverage_audit_draw.py`, every unmarked interval of each reviewed whatever its length — a sub-second interval can hold a missed serve, an edge interval a clipped rally; stage 2: the remaining 22 if stage 1 fails); independence (blind to the pipeline's output; a 20 % blind repeat by a second person or the same reviewer after 24 h, mirroring the boundary protocol §6.3; same-reviewer repeats never reported as inter-rater agreement); pass/fail per recording (0 missed rallies and no `play_bleeds` over 1 s → `audited_clean`; any missed rally → `contaminated`, corrective marking in the normal live pass, re-audit of that interval) and for the corpus (stage 1 missed-rally rate with its binomial upper 90 % bound ≤ 5 % of marked rallies → the audited recordings' negatives may be used; otherwise stage 2 before any negative is used); provenance (`<video>.coverageaudit.json`, `coverage_audit_v1`, bound to the marks' SHA-256 and the file fingerprint, never written by live tagging or phone sync; a proposed contract amendment `coverage.audit` and a new gate **G7** in the preregistration, both for the owner to approve, so that a `NON_RALLY` step requires `continuous` **and** lies inside an interval the audit recorded `clean` — never the recording-level verdict alone, never an interval's length); and what the audit does **not** do (it does not write or move rally marks — a found rally is handed to the marking pass; it is not Stage 1 and certifies no boundary).

Effort: stage 1 ≈ 12 recordings × (5–7 min of unmarked time at 2× + notes) ≈ 1.5 h for the auditor plus ≈ 20 min for the blind repeat. Tooling: the draw script (this PR, standard library, tested on synthetic inventories); a RallyLab command to write the audit sidecar from the auditor's filled sheet and a ledger row (a later reviewed PR; kind proposal in the protocol).

## 3. Priority C — the exporter `--export-rally-classifier-dataset`: dependency-aware implementation plan

**Scope.** A RallyLab headless command that writes `rally_classifier_dataset_v1` ([contract](RALLY_CLASSIFIER_DATASET_CONTRACT.md)) for one project, enforcing source admission, model-specific eligibility, grouped splits from the split manifest, the protected withheld closure, per-file hashes, the deterministic baseline replay, self-validation, and the exposure ledger. RallyLab 2.0 Phase 4's "versioned model-specific exporters" is its home (`docs/decisions/2026-11-02-rallylab2-overhaul-direction.md:726-742`: "Human-label eligibility · Declared or verified review coverage · Source lineage and split isolation · Protected-holdout exclusions · Exposure ledger recording · Reproducible manifests · Dataset versioning · Validation and preflight checks"); a stand-alone PR is acceptable if Phase 4 is far (research B4).

**Command shape.** `RallyLab --project <name> --export-rally-classifier-dataset <datasetName> [--out <dir>] [--variants r0,r0_prime] [--resume <dir>]`, dispatched like `--package-l2` (`HeadlessProjects.swift:366-371`), implemented in a new `RallyLab/RallyClassifierExporter.swift`. Steps, each fail-closed:

1. **Manifest and audit.** `buildManifest(audit: true)`; `hard == 0` or stop (as `LineagePackage.plan`, `:125`). Record the four hashes for the dataset manifest's `splitManifest`.
2. **Closure.** `ReservedVideos.lineageWithheldNames(in:)` expanded through fingerprint, `sourceId`, `sessionId`, `venueId` and alias groups (`ReservedVideos.swift:79-120`); any error stops. The closure (names, source ids, fingerprints) and its hash go into the manifest's `withheld` block.
3. **Plan.** Candidates = manifest rows with `split ∈ {train, dev_val, tune}` and `ralliesMarked == true`; refuse the run if any candidate is in the closure or shares an identity or alias group with a withheld row (`sharedIdentity`, `LineagePackage.swift:146-159`). Write `manifests/rally-classifier/<stamp>-plan.{json,md}` first, never overwritten.
4. **Admission and eligibility.** `SourceRegistry.load(root:)` (`SourceRegistry.swift:268-326`); per candidate `admission == admitted` and `eligibility[.rallyClassifier] ∈ {standard, restricted}` (`TrainingEligibility.assess`, called through the registry, not re-implemented); `fullVideoNegatives` level and reasons copied into the recording record; `recordingType` from the footage-properties record (`unknown` when none).
5. **Marks and coverage.** `<video>.rallylabels.json` (`RallyMarkRecord {startTime, endTime, kind?, contacts?}`, `Labeler/Shared/RallyEvents.swift:70-75`; nil kind = rally, provenance `legacy_nil_kind`; `startTick` = `contacts[0]` of kind serve when present else `startTime`); `<video>.rallyevents.json` when present (`rally_event_truth_v1`: contact/dead earliest–latest, `nonRallyActivity` spans, coverage, `stage1Complete`); `coverage.state` = `stage1_complete` / `declared_complete` / `partial` / `none`; `coverage.audit` from `<video>.coverageaudit.json` when the amendment is approved. Cut ranges from the session once #135 is on `main`. The marks' SHA-256 into `labelProvenance`.
6. **Evidence.** Per recording, `VideoProcessor` live with `collectFrameEvidence = true`, `ProcessorConfig()` as committed, `heatmapOnly`, `ball_heat` (L1), camera from the card (`withCamera(of:)`), rotation not applied — exactly as `TrainingDataExporter.swift:176-189` runs it, plus the serve emission times: the exporter runs its own `ServeWatch` over the on-court boxes in lock-step (as `EvidenceReplayer.swift:71-78` does) and records, per step, whether a serve was **emitted at that step** and its contact offset (`serve_emitted`, `serve_contact_offset`), never a retrospective flag. Steps = one line per `FrameEvidence` in time order, `rcf_v1` columns mapped from `FrameEvidence` fields (contract §4.1), `seg` by the contract's §3 rule, `y`/`w` by §5 (the exporter and the validator implement the same rule; the validator is the backstop). ≈ 3–5 min per recording on the Mac → ≈ 2–3 h for 34; `--resume` keeps finished recordings (their hashes are re-verified).
7. **Baseline.** Per variant (`r0` at the committed config; `r0_prime` at the D-029 settings), `EvidenceReplayer.decidedRallies` on the full `FrameEvidence` with C3's pre-merge raws → `baseline/<id>.json` (contract §3a) with the variant's `configSha256` (C2). The exporter asserts, per clip, that padding the stored pre-merge raws by the Swift builder reproduces the stored padded span (the same check the Python `pad_and_merge` performs).
8. **Staging, hashes, manifest.** Everything is written to `<out>/.staging-<name>/`; `stepsSha256`, `baselineSha256`, `stepCount`, `labelCounts` computed from the files; `dataset-manifest.json` last; the dataset digest by `DatasetSplitManifest.canonicalFileHashes` + `canonicalDigest` excluding the manifest (the registry's convention, `LineagePackage.swift:396-464`).
9. **Preflight (Swift, fail-closed subset) then the Python validator.** The Swift preflight re-reads the staged folder and checks: no withheld name/source/fingerprint present; no stray file; every hash matches; counts match; every recording `admitted` and eligible; closure non-empty and its hash right. Then the command runs `python3 scripts/rally_classifier/validate_dataset.py <staging> --withheld <closure.json> --json` (the repo's validator, which checks the full contract) and requires `ok == true`; if `python3` is unavailable the run **fails** (never "validated later"). The validator's report is written beside the plan. A thrown error removes the staging folder (as `MultiFramePackage.swift:784-797`).
10. **Ledger, then move.** `ExposureLog.record(videos:kind: .trainingPackage, ref: "--export-rally-classifier-dataset <name>")` for every packaged recording (`DatasetSplitManifest.swift:609-646`; a failed write throws and the export fails, `CLAUDE.md`: unwritable ledger aborts); only then `mv .staging-<name> <name>` (the `--export-net-dataset` order, `HeadlessProjects.swift:1095-1134`). The report `manifests/rally-classifier/<stamp>-export.{json,md}` carries the dataset identity `(name, digest, manifest SHA-256, split hashes, detector digest, config SHA-256)` for the registry row and the preregistration's `not fixed` fields.

**Every consumer honours exclusions (D-002).** The exporter is a new consumer of the pipeline on sessions; the PR lists how it refuses: closure refusal in step 2–3 before any video is opened; `SourceRegistry` admission in step 4; cut ranges masked in step 5–6 once on `main`.

**Tests (RallyLabTests + scripts/tests).** Synthetic project fixtures: a withheld name among candidates → refused before any video is read; a shared alias group → refused; `unknown` type with standard negatives cannot arise (eligibility comes from the registry); feature mapping from a hand-built `FrameEvidence` sequence → the expected `rcf_v1` row (nulls, counts, `y_above_net` tie, serve emission causality); `seg` breaks across a synthetic cut between two frames; baseline pre-merge raws reproduce the padded spans; the staged output of a synthetic run passes `validate_dataset.py` (the Python suite gets a checked-in Swift-written fixture); preflight failure removes the staging folder and writes no ledger row; a failing ledger write fails the export and leaves no dataset folder. Build: `scripts/build.sh both` (C2 touches a shared file).

**What the exporter does not do.** It does not confirm types, does not change splits or the closure, does not write marks, does not run on protected recordings, does not train. It is model-specific (rally classifier) and versioned (`rally_classifier_dataset_v1`); `rcf_v2` (Kalman velocity, gate internals) is a later contract and a later exporter branch.

## 4. Priority D — independent evaluation footage

**The constraint.** D-002: `final_test` is "reserved for recordings with no prior exposure". D-017: the 16 lineage-holdout recordings "must never be described as an untouched final test"; D-015/D-016: "the independent final test waits for new footage collected after the ledger existed". All 34 candidates are in both detectors' training packages and 26 were scored for decider selection; the 7 `*_extra_self_*` candidates were pre-tracked (`CANDIDATE-BLOCKED`) and carry no rally marks; tester clips are padded rallies only.

**Recommendation: collect new footage, reserve it at import, mark it once, evaluate once.**

1. **What to collect.** At least 6 full recordings (not clips), ≥ 2 per surface (beach, grass, indoor), ≥ 2 camera placements (endline elevated; endline ground), ≥ 1 portrait, at least one venue and one day that no training recording shares, each 5–15 minutes with ≥ 15 rallies, ≥ 100 rallies in total; recorded on the owner's iPhone (continuous by construction) with the camera at the endline (the pipeline's assumption). Online footage is a poorer independent test (unknown venue relations, edits) and is not recommended for this set.
2. **How it enters.** Import as cards with `split = final_test` **before** any processing (the card's split wins, `DatasetStore.swift:197-207`; `ReservedVideos.reservedNames` covers `finalTest`, `:37-42`), with `sourceId`/`sessionId`/`venueId` confirmed through `--set-provenance` so the closure spreads to anything sharing them (`ReservedVideos.swift:79-120`) and `--audit-dataset` would flag a shared identity with a training recording as a hard finding. Never pre-tracked, never pulled through `--score-rallies`, `--render-pipeline`, the tuner, the Sampler or the Net labels tab (each refuses `reservedAsListed` names, D-002 grep list in `CLAUDE.md`). The manifest's `finalTestExposed` guard (`DatasetSplitManifest.swift:287`) fails the manifest if a row ever shows exposure.
3. **How it is marked — a dependency, not a given.** Once a recording is reserved as `final_test` it is in the withheld closure, and **today's annotation tools refuse the closure**: the Mac Stage 1 opener `EventReview.open` throws `withheld` before opening (`RallyLab/EventReview.swift:128-133`), the phone's `rally_events_save` raises `withheld: … is a withheld recording` for any account (`supabase/migrations/048_label_rally_events.sql:169-173`; migration 049 additionally hides protected rows from ordinary labelers), and the coverage-audit draw refuses withheld names by design (protocol §3.1). The owner's account changes none of this (Codex on PR #138). The route is therefore a **separately authorised protected-annotation workflow** — dependency **P1**, owner decision **D9**: a reviewed change under which a person (never a model, never the pipeline) may mark and Stage-1-review a `final_test` recording while its reservation stays in place, e.g. an owner-signed per-recording authorisation file (`manifests/protected-annotation-authorisations.json`: recording, purpose `final_test_truth`, who, when) that `EventReview.open`, the live-pass marking and the coverage-audit tooling honour for *person-only annotation* and that every model-facing consumer (scoring, tuning, packaging, pre-tracking, the Sampler, the Net labels tab) ignores; its ledger rows are the labeling kinds (`event_review`, `coverage_audit`) with the authorisation's id in `ref`, and that PR must show that `DatasetSplitManifest`'s `finalTestExposed` guard (`:287`) treats those kinds as labeling, not model exposure, or extend it so. Until P1 exists the new footage is imported, reserved and left **unmarked**; the reservation is never lifted temporarily to mark it. Marking then follows the live pass (D-028's S/D/M/N) and `EVENT_BOUNDARY_REVIEW_PROTOCOL.md` for frame-exact contact/dead; coverage is certified by the coverage-audit protocol (§2) or by `stage1Complete`, so dead-time metrics are defined on it.
4. **How it is used.** Once, per D-017 §4: a separate preregistered record names the one carried-forward candidate, the `rally_scoring` ledger row is written before the run, the FSM and the candidate are scored on the same evidence in one pass, and the record closes. No second look for selection. Until then the set exists only as cards and marks.
5. **The 7 candidates.** Keep them `final_test_candidate`; they are not independent (pre-tracked) and unmarked. They could serve, once marked, as a second *exposed* reference like the lineage holdout, reported as such — never as the independent test.

Owner decisions: whether to record this footage (D7, §6), when, and who marks it.
