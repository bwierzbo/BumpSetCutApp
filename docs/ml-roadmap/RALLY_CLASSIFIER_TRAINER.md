# Rally classifier trainer and fold tooling

The tools that will run [EXP-20261103-temporal-rally-classifier-prereg](experiments/EXP-20261103-temporal-rally-classifier-prereg.md) once the owner approves it: the fold draw, the feature functions, the decode contract and the nested training and evaluation protocol, for the candidates R1 (logistic regression) and R2 (small TCN) against the stored decider outputs R0 and R0′. They read a dataset of the [dataset contract](RALLY_CLASSIFIER_DATASET_CONTRACT.md) and nothing else. **Everything here has been run on synthetic data only.** The one command meant for the real dataset before approval is the dry run (§2), which fits nothing and scores nothing.

This page states what each module does, the exact commands, every place where the specification was silent or ambiguous and what was chosen (§4), the places where the preregistration could not be run as written with the amendments the owner accepted on 2026-11-14 and what each requires of a report (§5), and the adopted negative-coverage gate (§5a). The preregistration record, the decision log and the dataset contract are not edited by this change.

**As the tools stand, no real run can start.** `rc-v1-20261112` carries declared negatives that no audit has reviewed, so the gate refuses it (§5a, §7); a dataset under the audited label schema (`rally_activity_truth_v2`, written and validated by the exporter and validator change this branch builds on) needs the audit reviewed and a new export.

## 1. Modules (`scripts/rally_classifier/`)

| File | What it does |
|---|---|
| `validate_dataset.py` (existing) | The fail-closed validator. Three small readers were added for the trainer (`load_manifest`, `read_steps`, `read_baseline`), plus `dataset_identity` (folder name, manifest SHA-256, the contract's digest) and a `specs` argument on the synthetic writer so tests can build a larger dataset with the same builder. No rule changed. |
| `folds.py` | Draws the grouped folds (`fold_draw_v1`) and writes them, once, to their own file with the dataset identity they were drawn for and the per-fold report. `load` is the trainer's reader: it refuses a file drawn for another dataset or edited after it was written. |
| `features.py` | `derived_v1` (R1's 42 inputs: the 18 raw columns and 24 derived ones) and the 30 Hz `grid_v1` view with R2's windows. The one function the Swift extractor will have to reproduce. |
| `decode.py` | Probabilities → raw intervals (hysteresis, raw floor) → clips (the SegmentBuilder port), the 108-point grid, and `parity`, which rebuilds every stored baseline clip from its pre-merge raw spans and stops the run on one mismatch. |
| `evaluate.py` | Builds the reference scorecard's input from a recording and a set of clips, pools per-recording scorecards into tables, runs the paired group bootstrap and evaluates H1 and H2 as worded — each also without the handheld recordings (§5.10). Every rally metric is `scripts/scoring/reference_scorecard.py`'s. Renders the report. |
| `trusted_negatives.py` | The adopted gate (§5a): a recording's trusted time read from the manifest (Stage 1 verified coverage, or the audit's reviewed-clean intervals), the trusted and untrusted negative steps and seconds per recording, group and fold, and the two verdicts G7 and G6 with every deficiency spelled out. Standard library only. |
| `tcn.py` | R2 in PyTorch (CPU, deterministic): model, windows, augmentation, loss, training. Imported only for `--candidate r2`. |
| `train.py` | The checks that precede a fit, the gate's refusal, the dry run, the nested protocol, the artefacts and the report. |

`scripts/train_rally_classifier.py` (the July within-video script) is not used, imported or extended.

## 2. Commands

```bash
D=<dataset folder>                 # e.g. ~/Movies/RallyLab/…/<name>; its folder name is the dataset's name
C=<withheld closure .json>         # the external closure the exporter validated against

# 1. Draw and freeze the folds (writes nothing if five folds are infeasible; never overwrites)
python3 scripts/rally_classifier/folds.py "$D" --out folds-<dataset>-s20261103.json --withheld "$C"

# 2. Readiness — the only run for the real dataset before approval: fits nothing, scores nothing
python3 scripts/rally_classifier/train.py "$D" --folds-file folds-….json --withheld "$C" \
    --candidate r1 --net present --seed 20261103 --out runs/readiness-r1 --dry-run

# 3. After approval: each candidate in each net condition (four runs)
python3 scripts/rally_classifier/train.py "$D" --folds-file folds-….json --withheld "$C" \
    --candidate r1 --net present --seed 20261103 --out runs/r1-present
python3 scripts/rally_classifier/train.py "$D" --folds-file folds-….json --withheld "$C" \
    --candidate r2 --net present --seed 20261103 --out runs/r2-present --r1-run runs/r1-present
# … and the same two with --net ablated
```

`folds.py` options: `--folds N` (default 5, at least 3: one fold held out, one chosen on, the rest trained on), `--seed` (default 20261103), `--stratify every-fold|where-feasible` (default `every-fold`), `--max-shuffles` (default 1000). `train.py` refuses, before any fit: a missing or unreadable closure file; a dataset the validator does not pass; a baseline `r0` that is not at the committed settings (preroll 2.0, postroll 0.5, join 1.3513, minimum 2.6131, serve-primed start on) or an `r0_prime` not at the D-029 ones; a folds file whose dataset name, manifest SHA-256 or digest is not this dataset's, or whose assignment is not what its seed draws; a SegmentBuilder port that fails parity; a run folder that is not empty; a label schema other than `rally_activity_truth_v1` / `_v2`; a stored matched baseline `r0_no_net_rule` that is not r0 with only the above-net rule off (§5.9); under `rally_activity_truth_v2`, a negative step with loss weight outside trusted time (§5a). **A real run is also refused when the negative-coverage gate is not met** — by `run`, the one function that fits, so no caller goes round it; the dry run reports the same deficiencies and exits 0 with the readiness report.

A run folder: `fold<k>/weights.json` (R1) or `weights.pt` + `weights.json` (R2), `fold<k>/calibration.json` (the temperature, δ of §5.8 and the limitation), `fold<k>/decode.json` (the point, the selection and any fallback used, §5.7), `oof.jsonl` (one line per step: recording, fold, tick, logit, calibrated p), `scorecards/<variant>/<recording>.evaluation_v2.json` for the candidate and every stored baseline variant, `report.json`, `report.md`. A dry run: `readiness.json`, `readiness.md` — the per-fold counts, the gate with its deficiencies, the exposure the manifest records, the baseline asymmetry and δ per fold from the counts. The report's identity block carries the dataset identity, the folds file's SHA-256 and draw, the SHA-256 of every script involved and the Python / numpy / torch versions — what the preregistration's §9 asks for.

Tests: `python3 -m unittest discover -s scripts/tests -p 'test_rally_classifier_*.py'` (folds: standard library; the rest need numpy; R2's need torch and are skipped without it). They build their datasets with the validator's synthetic writer (`scripts/tests/rally_classifier_synthetic.py`), in three shapes: every continuous recording Stage 1 verified (trusted: the default, so the protocol's tests can run), declared complete (the shape of `rc-v1-20261112`), and audited (`rally_activity_truth_v2` with `coverage.audit` records). `test_rally_classifier_amendments.py` holds the tests for §5's reporting requirements and for §5a.

## 3. What a run does

1. Validates the dataset with the external closure, checks the baseline settings, loads and verifies the folds file, runs the parity check, and computes the trusted negatives and the gate (§5a). A dataset that does not meet the gate goes no further.
2. For each outer fold k of K: the nested fold is (k + 1) mod K. On models fitted to the other K − 2 folds it chooses, on the nested fold: R1's penalty from {1e-4, 1e-3, 1e-2} or R2's stopping epoch (≤ 40) by loss; one temperature; one decode grid point by the D-007 objective against R0 on the same recordings. It then refits on the K − 1 training folds and predicts, calibrates, decodes and scores fold k. Nothing of fold k is read before that last step (a test replaces fold k with nonsense and shows every choice unchanged).
3. Scores the candidate's clips and the stored `r0` / `r0_prime` clips of every recording with the reference scorecard, and reports per fold, per surface, per group and pooled over the standard recordings, restricted recordings apart, with paired group-bootstrap 90 % intervals (1,000 draws, seed 0, groups as units) for every difference from R0.
4. Writes the report. Besides the tables it always carries, in this order: what the evidence is (§5.13); the choices per fold; the decode fallbacks used, or that none was (§5.7); H1 or H2 with the handheld sensitivity (§5.10); the calibration limitation, δ per fold and the reliability tables (§5.8); the baseline asymmetry (§5.9); the gate (§5a); the handheld recordings apart, and the standard recordings on which the above-net rule never ran; the secondary comparison against a matched baseline when the dataset stores one; the caveats.

Labels: only steps with `w` = 1 enter a loss, a class weight, a standardisation or a temperature. `TRANSITION`, `UNKNOWN` and `EXCLUDED` steps contribute nothing (tests show their targets and measurements can be replaced without moving a gradient or a fit). Steps inside a cut range or a time-breaking span are never decoded; missed serves and other excluded spans are masked by the scorecard, never counted as negatives.

## 4. Choices where the specification was silent or ambiguous

**Folds (`fold_draw_v1`)**
1. The deal carries on from one surface to the next rather than restarting at fold 0, so folds differ by at most one group (18 groups → 4, 4, 4, 3, 3; §2 says "5 folds of 3–4 groups") and a surface with at least K groups is in every fold by construction. See §5.2.
2. A re-shuffle shuffles the same list again with the same `random.Random(seed)`; the accepted attempt's number is recorded. Limit 1,000 attempts.
3. Rally balance: every fold's rally count within 25 % of the mean, inclusive, counting all recordings of the fold (restricted ones too).
4. A group whose recordings have different surfaces takes the most frequent (ties: alphabetical) and is listed in the report.
5. `--stratify every-fold` (default) is the preregistration's wording; `where-feasible` is the owner's "stratify where feasible" — opt-in, recorded in the file, with the surfaces that are not in every fold listed.
6. Durations are step time: a step stands for the time since the previous step of its segment. Positive = `ACTIVE_RALLY`; valid negative = `NON_RALLY` + `NON_RALLY_ACTIVITY`.
7. The folds file reports negative coverage as a count, a fraction and two comparisons (count ≥ 12; fraction ≥ 12/18) of groups with *labelled* negatives, never as a verdict. The gate itself — G6 as the owner accepted it (A3), counted over trusted negatives — is `trusted_negatives.py`'s (§5a); a frozen folds file keeps the report it was written with.
8. `folds.py` validates the dataset before drawing. The manifest's own `fold` field is ignored. A copy of the dataset under another folder name is another dataset (the contract: the folder's name is the dataset's name).

**Features**
9. Window membership is decided on integer ticks: trailing (k − W, k], forward (k, k + L]. Rates and durations use seconds.
10. A null is 0; a null `dt` is the nominal period, and so is the `dt` of every segment's first step (the stored value there is the gap or cut behind the break — another segment's time, and an outlier of seconds in a column that is otherwise nearly constant). Within a segment `dt` still reaches 0.5 s against a usual 0.029 s; nothing clips a standardised input, because the preregistration provides for no clipping. The only presence indicator is `has_y_above_net` (R1), because a 0 there would read as "at the net top". R2 gets none beyond `cell_missing`, since the preregistration fixes its inputs at 19.
11. `derived_v1` is 24 columns (list in `features.py`), 42 inputs with the raw ones; the research document estimated ≈ 45.
12. `mean_speed` averages consecutive step pairs that both lie in the window and both have a selected track; `log_size_rate_1s` is the least-squares slope of ln(size) against time; a window with nothing in it gives 0.
13. Serves are looked up within the step's segment; `t_since_serve_contact` uses the latest contact, at or before the step, among serves emitted no later than the bound.
14. Grid cells are 20 ticks wide on the tick timeline — cell = (tick − first tick) // 20 — so membership is integer-exact. The grid needs 600 / `samplingHzNominal` to be whole.
15. R2's windows: 600 cells, hop 300; a window answers for its middle 300 cells (the first from the segment's start, the last to its end); cells past the segment's end repeat the last cell. See §5.5.

**Decode**
16. An interval starts at the first step of the high run that opened it and ends at the first step of the low run that closed it. A run's length is its last tick minus its first; thresholds are inclusive.
17. An interval is closed at **every** segment break — a frame gap over 0.5 s as well as a cut or a time-breaking span — and ends one cell after the segment's last step, clamped to the duration.
18. Segments inside a cut range or a time-breaking span are never decoded (their predictions are still in `oof.jsonl`).
19. The SegmentBuilder port is the validator's `pad_and_merge` — the function the contract names — not a second transcription. It was read against `SegmentBuilder.swift` line by line: equal for raw rallies inside the recording, which `finalize_with_raw` enforces; it also refuses a pre- or post-roll that is not a whole number of ticks. Parity compares each clip's padded span and its raw spans.

**Training**
20. R1's objective is Σ cᵢ·BCEᵢ + ½·penalty·‖β‖², Σ cᵢ = 1, each class half the weight, intercept not penalised. See §5.4 for the optimiser.
21. R1's penalty is chosen by the nested fold's loss (the same data term, with the inner folds' class weights); a tie goes to the larger penalty.
22. The temperature minimises the plain cross-entropy of the nested fold's weighted steps, by golden-section search over [0.01, 100]; a value at the edge is flagged `atSearchBound`.
23. The decode point is chosen on all recordings of the nested fold, restricted ones included (they are trained on). Dead-time retention and false clips come from its fully marked recordings. See §5.7 for the two cases §5 of the preregistration does not cover.
24. R2: one convolution per residual block (that is what gives 125 cells and ≈ 27 k parameters: 26,433); not class-balanced (the preregistration balances R1 only); loss on the cells a window answers for; window order shuffled per epoch; the earliest epoch on a tie; the refit runs for the chosen number of epochs with the same seed.
25. R2's augmentation: at most one dropout run per window, 3–15 cells, placed uniformly; besides the columns §4 lists, `is_projectile` is zeroed and `ball_y_any` and `y_above_net` nulled, because the contract ties them to the nulled ones; confidence jitter is drawn per cell and clipped to [0, 1].

**Evaluation**
26. Scoring fixture: cut ranges and time-breaking spans are both passed as cuts; the contact is the rally's start; `fullyMarked` is coverage complete and negatives `standard`.
27. Headline tables hold the standard recordings; restricted recordings are scored identically and reported apart, as a group and one by one.
28. Raw boundaries are the contract's (one span per clip, the union of the raws it joined). The clips' pre-merge raw spans are scored as well (`preMergeRawBoundary`) so that the model's own merges can be told from the padding's; IoU ≥ 0.3 is reported beside 0.5.
29. Pooled numbers are ratios of sums over recordings; boundary errors are pooled over matched rallies; medians are pooled and get no interval.
30. Bootstrap: a draw in which a ratio is undefined is skipped and the number of draws used is reported; a table with one group has no interval. A table under 3 groups or 30 rallies is marked indicative only.
31. H1's "false clips" is the pooled count over fully marked standard recordings. H2's "no worse than R1's" is judged on the point estimates.
32. `unprimed`: a decoded interval with no serve contact within 3 s of its start. `uncertain time`: runs of calibrated p in [0.3, 0.7] lasting at least 2 s. Calibration is reported as a ten-bin table per surface, not a drawn diagram.

**Reports under the accepted amendments, and the gate** (added 2026-11-15)
33. A recording is handheld when its manifest `camera`, lower-cased, starts with `handheld` — RallyLab's own test (`NetLabels.swift`, `camera.lowercased().hasPrefix("handheld")`). `camera` is the clip plan's free text (`StandardClipPlan.swift`); every value that exists there or in `rc-v1-20261112` was checked — `End line, elevated (stands/tripod 2m+)`, `End line, ground level`, `Sideline / near net`, `Tripod / corner`, `Handheld / corner`, `Online (CC-licensed)`, `Extra` — and only `Handheld / corner` is handheld. In `rc-v1-20261112` that is `grs_hnd_shade_port_self_02` (continuous, standard) and `ind_hnd_dim_land_self_02` (edited, restricted). The manifest carries no footage-properties trait, so a camera that was held by hand under another `camera` value cannot be told.
34. The table "Handheld recordings (apart)" holds every handheld recording, standard and restricted, and names them; a restricted one contributes no dead-time or false-clip number there, as everywhere. The sensitivity analysis is on the headline (standard) tables — pooled, per surface, per fold, per group, against R0 and against a matched baseline — and removes the handheld recordings from both sides of each comparison; a table that holds none says so, and one left empty says that. The verdict of H1 / H2 is the headline's; the evaluation without the handheld recordings is printed beside it as "the same verdict" or "a different verdict" and never replaces it.
35. A fallback's record: `recall_constraint_not_met` carries R0's complete rallies, the most any grid point reached, the rallies, how many short, both recalls, the number of points at that best, the same counts recording by recording at the chosen point, the number of points that met the constraint (0) of 108, and the rule applied; `dead_time_retention_undefined` carries the number of fully marked recordings in the nested fold and the rule applied. Both can apply to one fold.
36. δ is reported twice per fold, from the counts of steps with loss weight: for the model the temperature was fitted on (the inner folds) and for the model that is scored (the training folds), with the class frequency n⁺ / (n⁺ + n⁻) at which the scored model says 0.5 before the temperature. The dry run reports the same numbers, since they need no fit.
37. The table "above-net rule never ran" holds the standard recordings whose manifest `net` is null: the manifest's net is the first detected net of the evidence, which is what the rule looks for.
38. Exposure is counted from the manifest's per-recording `exposure` rows as they were at export: recordings with at least one row of each kind, recordings per training-package ref, and recordings with no row. The rows a dataset's own export adds to the ledger are written after its manifest and are not in it.
39. Trusted negatives. A negative step is a step labelled `NON_RALLY` **or `NON_RALLY_ACTIVITY`** with loss weight: the owner's sentence admits two sources of trust and no third, so a marked non-rally-activity span outside both is untrusted as well (no dataset holds one today). "Eligible Stage 1 verified coverage" is `coverage.state` `stage1_complete` with `fullVideoNegatives` `standard`. The audit record's `state` is reported and not used: trust is per reviewed-clean interval (audit spec D7). A group contributes when its trusted-negative time is above zero. Two-thirds is of all the dataset's groups, rounded up (25 → 17). A `rally_activity_truth_v1` dataset whose only negatives with loss weight lie under Stage 1 verified coverage meets G7 — no real dataset is like that; the synthetic default is, which is how the protocol's tests run on this branch.
40. A caveat corrected. The report's caveat on the above-net rule said `rcf_v1` does not hold what that rule reads. It does hold the rule's height input — column `ball_y_any` is `EvidenceReplayer.ballHeight`, clamped to [0, 1], on the steps' frames — and the manifest holds the net box. What does not exist is a verified port of `NetClearanceRule`, or anything in today's dataset to verify one against. The caveat now says the trainer does not apply the rule because it has no verified port of it; nothing else in it changed, and no caveat was removed.

## 5. Where the preregistration could not be run as written — amendments accepted 2026-11-14

The preregistration's §11.5 lists these as A1–A13. The owner, 2026-11-14: "Accept A1–A13 as proposed, with these reporting requirements" — quoted under the items they bind — and "Record the accepted amendments and incorporate any necessary reviewed tooling changes." The acceptance is recorded in the preregistration and the decision log by their own change; this section states what the tools do under each amendment. Where an amendment offered a choice, "as proposed" is the reading the trainer already implemented.

1. **Folds in the dataset manifest (§2, §9) — A1, accepted.** The fold draw lives in an immutable file of its own, tied to the dataset's name, manifest SHA-256 and digest; the dataset is never edited and the manifest's `fold` stays null. The folds file's SHA-256, seed and shuffle number are what §9 records.
2. **The fold procedure (§2) — A2, accepted.** §2's procedure is `fold_draw_v1` as defined in `folds.py` (the deal carries on across surfaces); its demonstration draw is dropped. On the corrected 25 groups it gives five folds of five; the frozen draw is the preregistration's §11.2.
3. **Five folds on corrected groups, and gate G6 (§2a) — A3, accepted.** Five folds are feasible on the corrected groups. G6 is now "at least two-thirds of the groups, and at least two groups with valid negatives in every fold". With G7 adopted it is counted over trusted negatives only (§5a).
4. **R1's optimiser (§3) — A5, accepted.** "Full-batch gradient descent" fixes neither a step size nor an iteration count. The objective is strictly convex, so the trainer finds its one minimiser by full-batch Newton steps (gradient under 1e-10), deterministically.
5. **R2's margins (§3) — A6, accepted.** With 600-cell windows and a 300-cell hop each window answers for its middle 300 cells: a 150-cell margin, more than the 63 cells the receptive field needs.
6. **Per-rally classes (§6) — A7, accepted.** The report gives one class per rally from the reference scorecard's own fields — preserved (complete, alone in its clip), merged (complete, sharing its clip), clipped, missed — and the raw scorer's split and merged counts. The six-class taxonomy would need the scorecard extended first, in its own reviewed change.
7. **Decode selection (§5) — A8, accepted; "report whenever the decoder-selection fallback is used, including why the recall constraint was not met."** The two fallbacks are as before: when no grid point reaches R0's complete rallies on the nested fold, the point with the most complete rallies is taken (then least dead time, fewest false clips, earliest); when the nested fold has no fully marked recording, dead-time retention is undefined, so false clips and grid order decide. What changed is the record (§4.35): each fallback used is written into that fold's `decode.json` and into the report's "Decode-point selection fallbacks" section with its counts and its reason, and a run in which none was used says so in the same section and on the command line. The dry run still lists, in advance, the folds whose nested fold has no fully marked recording.
8. **Calibration after class-balanced training (§3, §5) — A9, accepted as written; "document the calibration limitation caused by class-balanced logistic regression."** No bias term is added; calibration is one temperature. The limitation, stated in every report (`train.CALIBRATION_LIMITATION`) with the numbers per fold: R1 weighs each `ACTIVE_RALLY` step 0.5 / n⁺ and each negative step 0.5 / n⁻. A loss that weighs the classes by a and b is minimised, input by input, where σ(z) = a·p / (a·p + b·(1 − p)), that is z = logit(p) + ln(a / b); here ln(a / b) = **δ = ln(n⁻ / n⁺)**. So R1's logit is the unweighted model's plus δ — exactly so for the minimiser of a well-specified model, slopes unchanged; a test fits both on 200,000 synthetic steps whose classes overlap and finds the intercepts δ apart to within 0.03 and the slopes equal to within 0.03. A temperature maps z to z / T: logit 0 stays p = 0.5, where the class frequency is n⁺ / (n⁺ + n⁻) rather than one half, so no temperature removes δ. R1's reported probabilities are therefore decode scores, **not calibrated class frequencies**; the reliability table is still reported, per surface, and shows the offset. The decode thresholds are chosen per fold on the same scores, so the clips do not depend on δ. On `rc-v1-20261112` the classes are close to balanced: δ of the scored models is +0.19, −0.06, −0.04, −0.02 and −0.13 for folds 0–4 (from the dry run's counts; nothing fitted) — at logit 0 a class frequency between 0.45 and 0.53. R2 is not class-balanced (δ = 0).
9. **The above-net rule (§3, §5) — A10, accepted; "retain the production FSM as the primary baseline and explicitly report its above-net-rule advantage. Investigate a matched baseline without this rule where practical, without changing the primary baseline or silently altering the existing dataset."**
   - *Primary baseline.* R0, the stored output of `EvidenceReplayer.decidedRallies` at the committed settings, stays H1's benchmark. Nothing in the trainer changes it.
   - *The advantage, reported.* Every report (and the dry run's) has a "Baseline asymmetry" section (`train.ASYMMETRY`): R0's stored clips passed the pipeline's above-net rule after SegmentBuilder; a candidate's clips go through the SegmentBuilder port only; the rule only removes clips, so it can lower R0's false clips and dead time in a way the candidate is not given, and nothing is corrected for it.
   - *What can be counted without a model.* Where the rule could act and where it never ran: it runs only on a recording with a detected net. In `rc-v1-20261112` 45 recordings have one (690 truth rallies, 533 stored R0 clips) and 4 do not (`bch_extra_self_04`, `ind_ele_bright_land_self_01`, `ind_extra_self_07`, `ind_gnd_bright_port_self_03`; 46 rallies, 55 clips) — on those R0 is already the matched baseline, and a run tables the standard ones apart (indicative only at that size). **How many clips the rule removed from R0 cannot be counted from this dataset:** the baseline files hold only the clips that passed, and the decider cannot be re-run from the steps (contract §3a).
   - *The investigation.* A matched baseline is practical, in a **new** dataset, with one exporter change — no Swift file is changed here. The rule is the last filter of `EvidenceReplayer.decidedRallies` (`RallyLab/EvidenceReplayer.swift:122–131`, after `finalizeWithRaw` at :90; the rally-score gate at :102–115 is off by default) and runs only when `cfg.enableAboveNetRequirement` (default true, `BumpSetCut/Models/Detections.swift:354`). The exporter replays that function once per baseline variant on the same evidence (`RallyLab/RallyClassifierExporter.swift:703–709`); its variants are `r0` and `r0_prime` (`:90–104`). A third, `ProcessorConfig()` with `enableAboveNetRequirement = false`, costs one more replay per recording and no detector run; its five stored settings equal r0's and its `configSha256` differs (the canonical config reflects every stored property, `Detections.swift:506–512`), which the dataset contract and today's validator already admit ("further variants … carry their own config hash"). It cannot be added to `rc-v1-20261112`: the dataset is sealed and the evidence is not stored.
   - *The trainer's side, already in place.* An optional variant named **`r0_no_net_rule`** (the manifest's naming: `r0`, `r0_prime`). A dataset that stores one that is not r0 with only the rule off — its settings not r0's, its config hash r0's, or a stored r0 clip not in it unchanged (the rule removes whole clips) — does not validate (`validate_dataset.py`, contract §10.3), so the trainer, which validates first, refuses it before any fit; r0 itself is held to the committed settings by the trainer. The report then counts the clips the rule removed, and gives every table a second time with `r0_no_net_rule` as the reference, under the heading "Secondary comparison"; its `r0 − r0_no_net_rule` rows are R0's advantage, measured. H1 and H2 are evaluated against R0 only. When the variant is absent the report says "Matched baseline not in this dataset" and what is missing.
10. **Restricted and handheld recordings (§2) — A4, accepted; "retain eligible continuous handheld footage, but report handheld recordings separately and include a sensitivity analysis excluding them."** `restrictedUse` is what `TrainingEligibility` says — the 18 edited recordings — and restricted recordings are always reported apart, as a group and one by one. The continuous handheld recording `grs_hnd_shade_port_self_02` is eligible and standard: it is trained on and is in the headline tables. ## 5a. The negative-coverage gate (G7 adopted; G6 over trusted negatives)

The owner, 2026-11-14: "Only explicitly reviewed clean intervals or eligible Stage 1 verified coverage may supply trusted negatives under the adopted G7 policy." "Verify that the final negative-coverage gate is met. If fewer than the required groups contribute trusted negatives, report the exact deficiency rather than weakening the gate." "Never modify a sealed dataset or frozen folds file in place."

- **Trusted time** is read from the manifest, never from a step's label (`trusted_negatives.py`). A recording's is: the whole recording when it has eligible Stage 1 verified coverage; its reviewed-clean intervals (`coverage.audit.cleanIntervals`, half-open ticks) under the label schema `rally_activity_truth_v2`, when its full-video negatives are `standard`; nothing otherwise. An edited recording supplies no negative, whatever an audit record says.
- **G7** holds when every negative step with loss weight lies in its recording's trusted time. Under v2 the exporter and the validator promise it, so an untrusted one is a broken dataset: `prepare` stops — the dry run too — naming the recordings and the first tick (defence in depth; a test passes such a dataset through a validator that does not catch it). Under `rally_activity_truth_v1` there is no audit record: a declared-complete recording's negatives are counted and reported as **declared, not audited**.
- **G6** (A3): at least two-thirds of the dataset's groups, rounded up, contribute trusted negatives, and at least two such groups in every fold.
- **Enforcement.** `prepare` computes the trusted and untrusted negative steps and seconds per recording, group and fold. `run` refuses a dataset that does not meet both gates, before anything is fitted or written, with every deficiency — which groups, which folds, by how many. `--dry-run` writes the same in `readiness.{json,md}`, lists the deficiencies among its problems and exits 0. There is no flag that weakens or skips the gate.
- **What it reads.** `labelSchema.version`, and per recording `coverage.state`, `eligibility.fullVideoNegatives` and `coverage.audit` (`{state, auditSha256, drawId, cleanIntervals: [{startTick, endTick}]}`; absent or null for a recording never audited) — the shape of the coverage-audit design, decision D7. The exporter and validator change that writes and checks it is separate; `validate_dataset.py` and the contract are not edited here.
- **`rc-v1-20261112`** (label schema v1, every recording `declared_complete`, no Stage 1 record): **G7 not met** — 170,171 negative steps with loss weight (5,674.9 s) in 31 recordings are declared, not audited; **G6 not met** — 0 of 25 groups contribute trusted negatives, 17 required (17 short), and no fold holds one (2 short in each). The dry run reports it; a real run is refused. Neither the dataset nor the frozen folds file is modified: negatives become trusted in a new dataset, exported under v2 after the audit.

## 7. Known limits of what was verified

- Every test is synthetic. The synthetic baseline is written by the same `pad_and_merge` the port is, so parity on it cannot fail by itself; the tests therefore also break the port and the fixture on purpose, and check the port against hand-computed cases from the contract.
- **The dry run on the real dataset, 2026-11-13** (`rc-v1-20261112`; validation, fold check, parity and counts — nothing fitted, nothing scored):

  - The first parity run **failed on 14 of 1,265 stored clips**, each one a clip that reaches the end of a recording whose duration is past a half tick: the port clamped to the duration rounded to the nearest tick, and the builder clamps to `CMTimeMakeWithSeconds(duration, 600)`, which truncates (a 300.033 s recording ends at tick 180019). `decode.duration_ticks` now truncates; all 1,265 clips (r0 588, r0_prime 677) are rebuilt exactly.
