# Learned temporal rally classifier — research review and experiment preparation

**What this is.** The evidence-based review the owner asked for on 2026-11-03: what the repository already does to decide "rally or not", what a learned temporal classifier should predict and from which signals, which architecture to test first, how its predictions become clips, how it would reach the iPhone, and what stands between today and a credible first experiment. It is written against `main` at `5fcea89` (PR #134 merged); open PRs #110, #127, #130, #132, #133 and #135 were read but **nothing on their branches is treated as available**. Companion documents: the data-readiness and leakage audit ([RALLY_CLASSIFIER_DATA_READINESS_2026-11-03.md](RALLY_CLASSIFIER_DATA_READINESS_2026-11-03.md)), the dataset contract ([RALLY_CLASSIFIER_DATASET_CONTRACT.md](RALLY_CLASSIFIER_DATASET_CONTRACT.md)) and the preregistration draft ([EXP-20261103-temporal-rally-classifier-prereg](experiments/EXP-20261103-temporal-rally-classifier-prereg.md)).

**What it is not.** No model was trained, no sweep run, no label written, no split changed, no protected recording opened, decoded or scored. The protected holdouts (16 lineage, 5 legacy, their aliases) were touched only as names in `validation.json` and the split manifest. No application code changed; the one tool added (`scripts/rally_classifier/validate_dataset.py`) is standalone and reads only a dataset export of the contract's shape.

File references are `path:line` on `5fcea89`. Short names: VP = `BumpSetCut/Features/Processing/VideoProcessor.swift`, RD = `…/Logic/RallyDecider.swift`, SD = `…/Logic/ServeDetector.swift`, SB = `…/Logic/SegmentBuilder.swift`, BG = `…/Logic/BallisticsGate.swift`, KBT = `…/Tracking/KalmanBallTracker.swift`, CFG = `BumpSetCut/Models/Detections.swift` (`ProcessorConfig`), HBD = `BumpSetCut/Core/ML/HeatmapBallDetector.swift`, ER = `RallyLab/EvidenceReplayer.swift`, TDE = `RallyLab/TrainingDataExporter.swift`, PY = `scripts/train_rally_classifier.py`, W = `scripts/rally_classifier_weights.json`.

## 1. What the repository does today (evidence review)

### 1.1 The production decision path

The shipped pipeline (`main`) decides rally activity with the deterministic `RallyDecider` fed by the ball finder and the physics gate; nothing learned sits between the detector and the clips.

| Stage | What it produces per processed frame | Where |
|---|---|---|
| `HeatmapBallDetector` (`ball_heat` = L1 `scratch_768_1014`, canonical digest `09620ab77519bd9d`, recomputed on `main` 2026-11-03) | `[Peak{rect, confidence}]`: one peak per heat blob ≥ threshold (default 0.5 from the model metadata); `confidence` is the blob's maximum heat. No secondary-peak, spread or entropy statistic is exposed (blob size is computed and discarded) | HBD:35-40, 305-351 |
| windowed inference, `heatmapHop` 5 over 9-frame windows | every fed frame gets one answer from a window with neighbours on both sides, 4 frames late; frames are fed at ≈ 30 Hz whatever the source rate (`1/30 − 0.004` s spacing) | HBD:365-411; VP:258-264, 699-714; CFG:147 |
| off-court rejection, `KalmanBallTracker` | tracks with raw and smoothed positions, `estimatedVelocity`, `age`, `meanBboxArea`, `predictedPosition`, `kalmanState` (4×4 covariance); fresh = updated within `maxTrackStalenessSec` 0.3 | KBT:171-259; VP:36, 729-736 |
| `BallisticsGate.validateProjectile` on each fresh track over a 0.7452 s window | `ValidationResult{isValid, rSquared, curvatureDirectionValid, hasMotionEvidence, positionJumpsValid, confidenceLevel, gravitySignature, movementType, rejectionReason}`; fit curvature `a`, vertical span, max speed, apex, ROI error and loop excursion are computed but **not exposed** | BG:14-28, 50-237; CFG:83-87 |
| multi-court selection (`bestTrack`) | one selected track, chosen only among gate-valid tracks (score `0.5·confidence + 0.5·gravity + 0.10·size + 0.05·age`, stickiness 0.10) | VP:1308-1405 |
| `ServeWatch` / `ServeDetector` over all on-court boxes | a `Serve{toss?, contact, end, approaching, path}` emitted 0.5 s after its flight ends (size-trend flight: median log ball size rising ≥ 0.3/s, ratio ≥ 1.3, r² ≥ 0.6, ≤ 1.2 s) | SD:33-56, 58-91, 239-272; VP:764 |
| `RallyDecider.update(hasBall:isProjectile:timestamp:ballY:)` | a binary `inRally` with hysteresis: start when a projectile run ≥ `startBuffer` 0.1685 s (≤ 5 dropped frames tolerated) or when a primed serve accrues ≥ 0.6 s of projectile time; the start is dated at the serve's **toss** (`toss ?? contact`) when primed, else at the current frame, and re-dated backwards if a serve settles later; end when ≥ 1.0 s since the last projectile **and** ≥ 0.398 s since the last ball (2.0 s when the last ball was in the top 15 % of the frame), never before 1.1653 s | RD:83-91, 106-160, 177-222; CFG:193-215 |
| `SegmentBuilder` | raw ranges (decider start → the first inactive frame), then padded `[start − 2.0 (0.5 if raw < 2.5 s), end + 0.5]`, merged when the **padded** gap ≤ 1.3513 s (raw spans unioned), dropped when the padded length < 2.6131 s; then the above-net rule over raw spans | SB:61-135; CFG:218-221; VP:1031-1045 |

Three properties of this path matter for a learned replacement:

1. **Every decision is per frame with a 0.8 s memory** (`windowSec`, RD:35) plus a handful of timers. The decider never sees the next frame. Yet the product processes a *recorded* file, so a bounded look-ahead is legitimate; the pipeline already tolerates latency (heatmap answers 4 frames late; a serve settles 0.5 s after it ends; a rally start is re-dated after the fact, RD:85-91).
2. **The start is dated at the toss, truth is the contact.** `Serve.start = toss ?? contact` (SD:52) and `rallyStartTime = primedServe.start` (RD:154), while the scoring contract's truth start is the serve contact ([SCORING_CONTRACT.md](SCORING_CONTRACT.md) §1). The retune diagnostic measured the padded start offset at −1.6 s median (EXP-20261031 §2) and the raw decided start at +0.9 s (tune pool) / +0.1 s (evaluation pool) median against the marks (§7): the padding, not the raw start, is what reaches the toss. A classifier trained to the marks' start would learn the contact, not the toss.
3. **Merging decides on padded gaps.** Two rallies closer than preroll + postroll + join gap (2.0 + 0.5 + 1.3513 = 3.85 s) become one clip (SB:82-119). In the 34 declared-complete development recordings, **185 of 527** consecutive-rally gaps are under 3.85 s and 46 under 1.3513 s (readiness audit §3). The L1-vs-L2 diagnostic counted 186 of 449 marked rallies as *merged* under L1 at the committed settings, 138 of them in three recordings delivered as a single clip each (EXP-20261031 §2). Merging, not missing, is the dominant failure of the current path on this corpus; a per-frame classifier only helps here if its decode can close a rally inside a short gap, which §5 addresses.

### 1.2 The July 2026 logistic-regression experiment (EXP-20260705-rally-classifier-lr)

Commit `c11425b` (2026-07-05) added two things that are still on `main` and nothing else has used since:

- **`RallyLab --export-training-data [path]`** (TDE:114-212; GUI button `RallyLab/InspectorPane.swift:531`) writes `<video>.trainingdata.json` with one row per `FrameEvidence`: `t, ball, proj, r2, grav, x, y, size, dets, courtDets, conf, move, rej, cands` (TDE:23-38), the recording's `netTopY`/`netBottomY`, the rally marks as `labels` and the FSM's raw ranges as `baselineRaw`. Headless, the labels come from `<video>.rallylabels.json` decoded as `[LabeledRally{startTime,endTime}]` — **kinds are dropped**, so a `missedServe` mark becomes a positive rally label (TDE:167-170). The exporter has no reservation guard and writes no ledger row ([RALLYLAB2_PHASE0_AUDIT §3.2](RALLYLAB2_PHASE0_AUDIT_2026-11-02.md)), and nothing on `main` masks cut ranges (PR #135 is unmerged).
- **`scripts/train_rally_classifier.py`** (433 lines, numpy): 27 features (17 raw + 10 causal 1.0 s-window features, PY:101-158), class-balanced L2 logistic regression (PY:179-200), frames within 0.5 s of a label boundary excluded from training (PY:43, 169-174), **time-blocked out-of-fold evaluation inside each video** (6 blocks, PY:306-323), causal hysteresis decode (enter 0.7 / exit 0.3 with sustain, PY:49, 210-250) followed by the production merge and minimum-length rules applied to **raw** spans (production applies them to padded spans, SB:82-119), and a port of `RallySegmentationScorer` (IoU ≥ 0.5, tolerance 1.0 s).

Its one recorded result is on one recording, IMG_2806 (9 rallies, 299 s): the FSM was already 9/9 there, the learned model matched 9/9 and cut the boundary errors (startMAE 1.22 → 1.02 s, endMAE 0.71 → 0.44 s; frame AUC 0.965), registry row EXP-20260705. Reading the code adds four caveats that the registry row does not carry:

| # | Finding | Where | Consequence |
|---|---|---|---|
| F1 | **The saved weights are one video's fit.** The "final weights on ALL frames of all data" block is inside the per-export loop, so `rally_classifier_weights.json` is overwritten once per export and holds the last video's fit (`trainedOn: ["IMG_2806.mov"]`, bias 0.529) | PY:395-406; W | the weights file is not a corpus model; nothing in Swift loads it anyway (no `RallyClassifier` type exists on `main`) |
| F2 | **Five of the 27 features are one signal.** `trackPoint`, `rSquared`, `gravitySignature` and `movementType` are set only when the selected track passed the gate, and `rejectionReason` at frame level is always nil, because `bestTrack` selects only among gate-valid tracks | VP:751, 770-787, 1308-1405 | `has_track`, `has_r2`, `proj` and `r2 > 0` coincide (W: identical mean/std 0.2027/0.4020); `move_carried`/`move_rolling` never fire (std 1.0, weight 0). Rejected-track information lives only in `candidates[*].rejectionReason` and is not exported |
| F3 | **No cross-recording validation.** Out-of-fold means other time blocks of the same video; there is no recording group, no split manifest, no eligibility check | PY:306-323 | the 0.965 AUC says nothing about generalisation across venues, which is the question D-001 asks |
| F4 | **Decode differs from production.** Min length on raw spans (production: padded); no preroll/postroll; the IMG_2806 labels have no `kind` (pre-live-tag) | PY:244-250 | boundary MAEs are not the contract's raw-boundary errors |

The experiment is **feasibility evidence**: physics-gate signals aggregated over a one-second window carry rally state (the top weights were `win_r2`, `win_grav`, `t_since_ball`, `win_max_y`, `conf`). It is not evidence that a learned classifier generalises, and its artefacts (weights, exporter) are not reusable as they stand.

### 1.3 The L2 decider retunes (EXP-20261031, EXP-20261101 on PR #127) and D-029

Both retunes searched only the decider's joining and padding on the 9-recording tune pool and judged the best candidate on the other 17 diagnostic recordings (development evidence; all 26 are in both detectors' training packages). The accepted tradeoff (D-029, PR #132, proposed): L2 at join 0 / postroll 1.0 / preroll 2.0 / min clip 1.5 gives 137 preserved and 150 merged for 48 false clips and 4.43 s dead time per rally, against L1 committed at 127 / 159 / 29 / 3.81 s. Two of five preregistered bars failed in both plans. The records' own reading (§8) is that the knobs trade preservation against false clips and dead time along one axis: the decider has no way to open a rally without also opening on non-rally ball flight, and no way to close a gap between rallies without also cutting rallies with brief occlusions. That is precisely the kind of boundary a learned model over the same signals can move, and the reason D-029 §3 names the classifier as the next direction.

Two consequences for this plan: the **baseline** for the classifier experiment is `main`'s committed configuration with the L1 model (the task's instruction and the only configuration the product ships today), with the D-029 row reported beside it as a second reference and never substituted; and the 26 diagnostic recordings carry **selection exposure** for decider settings (tune 9) and acceptance exposure (eval 17), so neither pool can be presented as independent evidence for the classifier either (readiness audit §5).

### 1.4 What exists for Stage 1 truth and footage eligibility

- Stage 1 records (`<video>.rallyevents.json`, `rally_event_truth_v1`: frame-exact contact and dead instants with `[earliest, latest]`, visibility, kind, coverage, `nonRallyActivity | transition | uncertain` spans, `stage1Complete`; `Labeler/Shared/EventReviewRecord.swift:21-118`) exist as a schema and a tool (Mac tab, iPhone screen) and **as zero records on the Mac** (readiness audit §2). The 24-rally calibration pilot (D-004) has not been frozen or run (PR #102 held).
- `FootageProperties` and `TrainingEligibility` (PR #134, merged 2026-11-03) define per-model eligibility; **zero footage-properties records exist**, so every recording's rally-classifier verdict is `not_assessed` and its full-video-negatives verdict `not_assessed` (`RallyLab/TrainingEligibility.swift:131, 151`). Only a person's confirmation of the recording type establishes eligibility; a proposal never does.
- Cut ranges (D-030, PR #135) are not on `main`; the 2026-11-02 edited-footage scan is a list of proposals (RALLYLAB2_PHASE0_AUDIT §11.5), three of which are among the 34 declared-complete recordings.

## 2. What the model should predict (question A)

| Formulation | What the labels would need | What it yields | Verdict |
|---|---|---|---|
| **Per-step rally-activity state** `ACTIVE_RALLY` vs `NON_RALLY` (the D-010 activity axis), decoded into intervals | interval marks (serve contact → ball dead) and a trustworthy negative class | the full timeline; boundaries by decode; every scoring-contract metric follows | **primary** |
| Serve/start-event probability | a frame-exact contact per rally (Stage 1) | precise starts; nothing about ends or continuation | auxiliary head once Stage 1 truth exists; alone it cannot bound a clip |
| Rally-end (dead-ball) event probability | a frame-exact dead instant (Stage 1) | precise ends | auxiliary head, same condition |
| Sequence-level state classification (one label per window) | interval marks | coarse windows; boundaries no better than the window hop | rejected: the product output is a bounded clip, not a window verdict |
| Boundary detection conditioned on ball-track history (a detector over the FSM's candidate boundaries) | interval marks | re-scores the FSM's own cuts; cannot recover a rally the FSM never opened or split one it merged | rejected as primary; the FSM is the benchmark, not the proposal generator |

**Recommendation: per-step rally-activity probability with a bounded look-ahead, decoded into raw intervals by a fixed post-processing contract (§5).** Reasons: (1) it is the only formulation the existing labels support — 561 interval marks in 34 declared-complete recordings, zero frame-exact events; (2) it produces the product output directly (a raw interval per rally, then the unchanged padded export) and is scored by the scoring contract without translation; (3) it subsumes the FSM: the FSM is itself a per-frame activity decision, so the comparison is like for like on the same cached evidence; (4) the two event heads can be added later as auxiliary outputs of the same network without changing the dataset contract, once Stage 1 gives contact/dead instants with uncertainty. The label is the **activity** axis only; ball visibility is never a target and never inferred from it (D-010).

The target is defined exactly in the dataset contract §4: a step is `ACTIVE_RALLY` when its 600-tick time lies in a truth rally's half-open interval `[contactTick, deadTick)` (the scoring contract's convention), `NON_RALLY` only where the recording's negatives verdict is `standard` and its coverage is complete, `EXCLUDED` inside missed-serve / other / cut spans, `TRANSITION` inside the boundary ignore band, `UNKNOWN` everywhere else. Only `ACTIVE_RALLY`, `NON_RALLY` and `NON_RALLY_ACTIVITY` carry loss weight.

## 3. Input features (question B)

The feature set is split into what the pipeline already carries per processed frame, what is derived causally from it, what the model's receptive field supplies, and what does not exist yet. The dataset contract stores **raw measurements only** (`rcf_v1`); every derived feature is computed by the trainer from the stored sequence so that the Swift port reproduces exactly one function.

### 3.1 Raw per-step measurements (available in `FrameEvidence` today)

| Feature (contract name) | Source | Unit / range | Missing | Note |
|---|---|---|---|---|
| `t`, `tick`, `dt` | `FrameEvidence.time` (VP:774), tick = round(t × 600), dt to the previous step | s, ticks, s | never | steps are the frames the pipeline processed, ≈ 30 Hz in multi-frame mode; dt is a feature, not a constant |
| `has_ball` | `hasBall` = `!courtDets.isEmpty` (VP:752) | 0/1 | never | on-court detections only |
| `n_court_dets`, `n_dets` | `detections` with/without `isOffCourt` (VP:777-781) | count | never | |
| `max_conf` | max `BallDetection.confidence` (heat peak value) | 0–1 | null when no detection | the raw model confidence (product invariant) |
| `ball_y_any` | the decider's own `ballY` input: selected track's last raw y, else highest court detection midY (VP:755) | Vision y, 0–1, 1 = top | null | |
| `is_projectile` | `isProjectile` = gate accepted the selected track (VP:751) | 0/1 | never | |
| `sel_x`, `sel_y` | `trackPoint` (smoothed when `useSmoothedTrack`, VP:770-772) | 0–1 | null when no selected track (= not projectile, §1.2 F2) | |
| `sel_size` | selected `TrackCandidate.ballSize` (√ mean bbox area over 12 positions, VP:103-123) | normalised side length | null | aspect-dependent: the recording record carries `aspect` |
| `r2`, `grav` | `rSquared`, `gravitySignature` of the selected track's gate window | 0–1, 0–1 | null when not projectile | redundant with `is_projectile` for presence; informative for magnitude |
| `n_cands`, `n_cands_proj`, `n_cands_rejected` | `candidates` and their `isProjectile` / `rejectionReason` (VP:103-123) | counts | never | the only place a rejected track is visible; a second ball on another court shows here |
| `y_above_net` | `sel_y − detectedNet.box.maxY` | signed, normalised | null when no net or no track | the recording record carries `has_net` and the frozen net box; see §3.4 |
| `serve_flag` | a `ServeWatch` serve whose `[start, end]` covers `t` | 0/1 | never | **0.5 s look-ahead** (the serve settles after its flight ends, SD:239-272): declared as the one raw feature with latency |

Not stored, by design: `movementType` one-hots (never carried/rolling after the gate; airborne ≡ projectile), `rejectionReason` at frame level (always nil), `fromHeatmap` (always true in multi-frame mode).

### 3.2 Derived, causal (computed by the trainer and the Swift extractor from the stored steps)

Trailing windows of 1.0 s and 3.0 s over the steps of the same contiguous segment: ball fraction, projectile fraction, mean `r2`, mean `grav`, max `sel_y`, mean speed from finite differences of `sel_x/sel_y` (the Kalman `estimatedVelocity` is not in the evidence; adding it is an exporter change, listed in §7), time since last ball and last projectile (capped 3 s), **log ball-size rate over 1 s** (the serve detector's approach signal, the only net-crossing proxy that exists from an endline camera), count of gate rejections in the window. These are the July features generalised; the trainer's feature-set version (`rcf_v1 + derived_v1`) is recorded in the experiment.

### 3.3 Look-ahead (the model's, not the dataset's)

Production processes a recorded file, so information from frames after `t` is legitimately available at the inference point **within a bound the pipeline can hold in memory and checkpoint**. The bound is a property of the model, declared in the experiment (recommended `lookaheadSec = 2.0`): a non-causal receptive field of ±2.0 s for the temporal network, and explicit forward-window features (`fwd2_ball_frac`, `fwd2_proj_frac`, `t_until_ball`, `t_until_proj`, capped 2 s) for the logistic baseline so the two candidates see the same information. The validator refuses a dataset whose steps are not strictly ordered or whose segments cross a cut or time-breaking span, so no window can be built across non-footage; the trainer is forbidden from using the labels, the FSM's output, or anything beyond `lookaheadSec` as input. Nothing derived from future observations is stored in the dataset.

### 3.4 Dependencies: net geometry and camera motion

- **Net.** The pipeline's net is one frozen `DetectedNet` box per video (median of 8 sampled frames, VP:1415-1440) from `net.mlpackage`, which is Ultralytics-derived and leaves the public bundle before launch (D-012; the replacement net model is not this task's). The classifier therefore takes net geometry as an **optional, per-recording** input (`has_net`, the box) and must be trained and evaluated **with the net features ablated to null** as well, so that it functions without a net model. The preregistration carries both conditions. Nothing else in the pipeline depends on the net for the classifier's inputs (off-court rejection widens `n_dets` vs `n_court_dets` but both are stored).
- **Net-crossing events.** No reliable per-frame net-crossing signal exists; the endline camera sees the net as a horizontal band and the ball's approach as a size change. The log-size rate (§3.2) is the available proxy; a crossing event is deferred.
- **Camera motion.** No per-frame camera-motion indicator exists in the pipeline (the net is frozen per video, so it cannot report drift). Handheld footage is restricted for initial temporal training (D-031, `TrainingEligibility.rule(.handheld, …)`), and the two handheld recordings among the 34 are reported separately. A per-step global-motion feature is deferred to RallyLab 2.0 Phase 2 (characterisation), which produces spans, not per-frame signals; a per-frame indicator would be a new pipeline measurement and is out of this scope.

## 4. Architecture (question C)

Input per step: ≈ 16 raw features (`rcf_v1`), standardised with train-split statistics stored in the model. Steps ≈ 30 Hz; a 5-minute recording ≈ 9,000 steps. Estimates are analytic (parameter counts from the layer shapes; MACs per step), not measurements.

| Candidate | Input window / stride | Parameters | Compute (per step; per 5-min recording) | Memory | Core ML conversion | Parity risk | Verdict |
|---|---|---|---|---|---|---|---|
| **R0 — deterministic FSM** (`RallyDecider` + `SegmentBuilder` as committed) | 0.8 s memory, causal | none | negligible | negligible | n/a | none (it is production) | **benchmark and fallback** (D-001) |
| **R1 — regularised logistic regression** over causal 1 s / 3 s windows and 2 s forward windows (≈ 45 derived features) | ±3 s of steps | ≈ 46 | ≈ 100 MACs; < 1 M | KB | trivial (a `linear` layer) or plain Swift arithmetic | low: one feature function, one dot product; a Swift unit test against the Python reference on a fixture evidence stream | **first learned candidate** |
| **R2 — small non-causal TCN**: input projection 16→32, five residual blocks of dilated 1-D convolutions (kernel 5, dilations 1,2,4,8,16, 32 channels, GELU, dropout), 1×1 head; receptive field 125 steps ≈ ±2.1 s | fixed window of 600 steps (20 s) slid with hop 300, each step scored once from a window where it has ≥ 2.1 s on each side | ≈ 27 k | ≈ 27 k MACs; ≈ 240 M | < 1 MB weights; activations 600 × 32 floats | straightforward: trace with a fixed `[1, 16, 600]` input, `ct.convert` (the heat converter already pins `minimum_deployment_target`, `scripts/desktop_training/heatmap_to_coreml.py:60-66`) | moderate: padding at the window edges and the exact standardisation must match; parity test on real evidence within 1e-4 | **second candidate (the one capacity step)** |
| R3 — compact bidirectional GRU, hidden 32 | whole sequence, or 20 s windows | ≈ 10 k | ≈ 10 k MACs; ≈ 90 M | small | stateful Core ML (iOS 18) or an unrolled fixed window; recurrent ops convert less predictably and parity across sequence lengths is harder to pin | higher | **secondary ablation only** if R2 is not clearly better than R1 (roadmap Phase 8 step 3 names the GRU as the secondary ablation) |
| Transformers, end-to-end video models, learned spatial-heatmap encoders | — | — | — | — | — | — | out of scope (D-013 §3, roadmap Q7: scene-specific shortcuts with 167 videos) |

Against the ball detector (`ball_heat`, 524 K parameters at 768×432 over 9 frames per window, BASELINE.md §model inventory) every candidate here is at least three orders of magnitude cheaper; none changes the iPhone's processing time measurably. The on-device numbers in the preregistration are therefore a **gate, not a comparison axis**: measured once per candidate on the physical iPhone by the owner, with a bar of "no measurable increase in processing time per minute of video and < 5 MB added to the bundle".

**Recommendation.** Test **R1 first and R2 in the same preregistered experiment**, against R0. R1 is the gate: if a regularised linear model over the gate's own signals cannot beat the FSM on complete-rally recall at equal or lower dead time on grouped folds, the problem is the signals or the labels, not the model capacity, and R2 would only fit the 18 groups. R2 is included so that the one capacity step is judged on the same folds in the same run rather than after a look at R1's result. R3 is run only as an ablation of R2 and never as the ship candidate. The choice is grounded in implementation cost: R1 ports to Swift in an afternoon and its parity test is exact; R2 needs a converter, a fixed-window runner and an edge-handling contract; R3 adds stateful inference.

## 5. From predictions to clips (question D)

Everything below is **post-processing**, fixed before training and identical for every learned candidate; the learned part is only the per-step probability `p_t`. The FSM's `SegmentBuilder`, the padded export, the above-net rule and the product safeguards stay as they are.

| Step | Rule | Why |
|---|---|---|
| Smoothing | none beyond the model's own receptive field; `p_t` is used as emitted. A moving average would re-introduce the merge-vs-split trade the model is meant to resolve | |
| Calibration | `p_t` is calibrated on the **development folds' out-of-fold predictions** by temperature scaling (one scalar), fitted before any threshold is chosen; the calibration set never includes the recording being scored. Reported: reliability diagram per surface | thresholds then mean the same thing on every surface |
| Hysteresis decode | enter when `p_t ≥ θ_on` for ≥ `sustain_on` seconds, exit when `p_t ≤ θ_off` for ≥ `sustain_off` seconds; defaults θ_on 0.7, θ_off 0.3, sustain 0.2 s / 0.8 s (the July values) are the **starting grid**, and the final values are chosen on the development folds by the D-007 objective (minimise dead-time retention subject to complete-rally recall ≥ the FSM's on the same folds), never on a held-out set | the same grid for R1 and R2 |
| Short occlusions and gaps | a dip of `p_t` below `θ_off` shorter than `sustain_off` does not close the rally (that is what the sustain is for); the detector's own gaps (`dt` > 0.1 s, undecodable frames) are carried as `dt` and never interpolated | |
| Minimum duration | a decoded interval shorter than `minRallySec` 1.1653 s is dropped **before** padding (the FSM's own floor, RD:48); the padded `minSegmentLength` 2.6131 s then applies as in production | the raw floor removes a learned model's one-frame blips; the padded floor is the product's |
| Close rallies | the decoded raw intervals go through the **unchanged** `SegmentBuilder.finalizeWithRaw` (preroll, postroll, merge on padded gaps, drop) so that the export is exactly what production does today; a learned model that separates two rallies 2 s apart still delivers one merged clip under the committed settings. The experiment therefore reports **raw** merged/split counts (the model's doing) and **padded** merged counts (the product's padding) separately, exactly as the scoring contract distinguishes them. Whether the padding changes is a later product decision with its own evidence (D-029 §2 leaves the shipped configuration open) | the contract's rule: raw boundaries against event truth, padded clips against what the viewer gets |
| Replays, slow motion, cuts | the classifier never runs across a confirmed time-breaking span or a cut range: steps inside them are not footage (D-030; `TrainingEligibility`), the segment index breaks there, and the decoded intervals are masked exactly as the scorers mask X. Until cut ranges are on `main`, a recording with a scanner-flagged replay is `restricted` and reported apart | |
| False-start suppression | the serve-primed start stays a **safeguard**, not a feature of the decode: a decoded interval that begins more than 3 s before any serve the `ServeWatch` emitted and more than 3 s before its first projectile step is reported as `unprimed` in the diagnostics; it is **not** dropped in the experiment (dropping it would hide what the model does). A production rule may add it later with its own evidence | |
| Uncertain predictions | steps with calibrated `p_t ∈ [0.3, 0.7]` for longer than 2 s are counted as `uncertain time` per recording and reported; when more than 20 % of a recording's steps are uncertain, the recording's result is flagged and the **FSM's decision is used for that recording** in the fallback mode (below) | the product never ships a clip set from a model that did not know |
| Fallback | `ProcessorConfig.rallyDecision ∈ {fsm, learned}` with `fsm` the default until a validated change is approved; `learned` falls back to `fsm` per recording when the model file is missing, fails to load, produces non-finite output, or trips the uncertainty rule; the fallback is logged and reported in the processing metadata | D-001: the FSM is benchmark and fallback |

What is *learned* ends at `p_t`. What is *post-processing* is the calibration, the hysteresis and the raw floor. What is a *product safeguard* is the unchanged padded export, the above-net rule, the serve diagnostic, the uncertainty rule and the fallback. The experiment reports the first two; the third is unchanged production code.

## 6. Core ML integration strategy (deliverable 9)

Not implemented here; the shape the production PR would take, so the experiment produces artefacts that fit it.

1. **One extractor, two implementations, one parity test.** `RallyActivityFeatures.extract(steps:) -> [[Float]]` in the shared pipeline (a file in RallyLab's `membershipExceptions`, both targets build) and `scripts/rally_classifier/features.py` compute `rcf_v1 + derived_v1` from the same step sequence; a committed fixture evidence stream (synthetic, like the scoring fixtures) pins both to the same numbers within 1e-5. The standardisation vector ships inside the model metadata.
2. **Model artefact.** R1: coefficients as a small JSON resource read by Swift (no Core ML needed) — or a one-layer `.mlpackage` for uniformity. R2: `.mlpackage` converted by `scripts/desktop_training/rally_classifier_to_coreml.py` from the trained checkpoint with a fixed `[1, F, 600]` input; `minimum_deployment_target` as the heat converter; FP16 weights; compute units `all` (the model is tiny; the ANE is not needed). Canonical directory digest recorded in the registry like every model.
3. **Runner.** `RallyActivityModel` protocol with `fsm` (wraps `RallyDecider`) and `learned` (buffers steps, scores fixed windows with hop 300 and ±63-step margins so every step is scored once from the window where it has full context; the last window is padded by repeating the final step, a documented edge rule) behind `ProcessorConfig.rallyDecision`. Decoded raw intervals feed the unchanged `SegmentBuilder.observe/finalizeWithRaw`. `EvidenceReplayer` gains the same switch so RallyLab scores exactly what production would ship (D-008 parity test extended to the learned path).
4. **Checkpoint/resume.** The processing checkpoint already persists `StoredFrameEvidence` (`BumpSetCut/Models/FlywheelContribution.swift:63-77`), which **drops `candidates`** — `n_cands*` would be lost on resume. The production PR either extends the stored evidence (backward-compatible `decodeIfPresent`) or the runner re-derives those counts; this is a known plumbing item, listed in §7.
5. **Licensing.** No Ultralytics code or weights: the classifier is trained with plain PyTorch (or numpy for R1) on detector/tracker signals; the signals come from `ball_heat` (from scratch, MIT architecture). The net features are optional (§3.4) so the classifier does not bind the public app to `net.mlpackage`.
6. **Measurement.** On the physical iPhone, by the owner, per candidate: processing time per minute of video with the switch at `fsm` and at `learned` on the same three fixture recordings, peak memory from the metrics collector, bundle size delta. Recorded in the experiment before any promotion discussion.

## 8. Final recommendation (deliverable 12)

- **Is the data sufficient for a credible first experiment?** For a *development* experiment, **conditionally yes**: 34 declared-complete development recordings, 561 rallies, 18 recording groups (beach 5, grass 6, indoor 7), about 1.3 h of rally time and 1.5 h of declared non-rally time, with grouped cross-validation. The conditions are B1 (eligibility confirmed, otherwise there are no negatives at all) and B4 (an exporter that writes the contract). For *independent* evidence of the kind D-001 requires before production adoption, **no**: no set on hand is unexposed and marked (B3).
- **Exactly what is missing.** Confirmed footage type for the 34 (B1); cut ranges or a continuous confirmation for 3 of them (B2); a contract-writing exporter (B4); for independence, rally marks on recordings with no exposure — the seven lineage-holdout candidates (a labeling task) or new footage (B3). Frame-exact Stage 1 events are **not** required for the first experiment; they are required before any claim about boundary error finer than the legacy marks' own uncertainty.
- **Architecture to test first.** R1, regularised logistic regression over causal and bounded-look-ahead window features of the gate/tracker signals, with R2 (the small non-causal TCN, ≈ 27 k parameters, ±2 s receptive field) in the same preregistered run as the one capacity step; the FSM as the benchmark and fallback.
- **Minimum valid experiment.** R0 vs R1 vs R2 on the 34 recordings' L1 evidence under the dataset contract, 6 grouped folds stratified by surface (no recording group on both sides of any fold), the scoring contract's raw and padded metrics per fold, per surface and per group, with the D-007 objective for every decode choice and the preregistered keep / revert / need-data rule. One seed for R2; R1 is deterministic.
- **Dependencies.** Necessary: B1, B4, the validator (in this PR), frozen split-manifest hashes at export time. Deferrable: Stage 1 truth (boundary claims), the net model replacement (the net features are optional and ablated), Kalman velocity plumbing (T1), cut ranges on `main` (until merged, the three flagged recordings are restricted), the Core ML runner (production PR, after the result).
- **Approvals needed to execute.** (1) The owner's answers to B1, B2, B5, D1–D3; (2) authorisation of the exporter PR (T/B4) under the PR tier; (3) explicit approval of the completed preregistration with the dataset hashes filled in (D4); (4) GPU/desktop time is not needed — R1 and R2 train on the Mac in minutes.
